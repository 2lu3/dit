# トラブルシューティング

## 初期化されていないと表示される

Gitリポジトリのルートで `dit init --bucket ... --prefix ...` を実行し、`dit.toml` が存在することを確認します。

## remoteへ接続できない

`DIT_ACCESS_KEY`、`DIT_SECRET_KEY`、`DIT_ENDPOINT_URL` が設定されていることと、`dit.toml` のbucketとprefixを確認します。秘密情報は `dit.toml` やGitへ保存しません。

## push/pull が遅い

転送が遅いときは、`DIT_TRANSFER_CONCURRENCY` で並列数を調整できます。既定値は16で、`push` / `pull` / `sync` に共通です。8 MiB 以上のファイルは分割して転送します。

`pull` と `sync` では複数ファイルを同時にダウンロードします。ファイル内の分割転送も含め、ダウンロード全体で並列数の上限を共有します。`push` は1ファイル内で並列転送します。

```console
$ DIT_TRANSFER_CONCURRENCY=32 dit pull
```

既定の16と比較し、速くなる場合に採用してください。継続して使う設定は、リポジトリ直下の `.env` に `DIT_TRANSFER_CONCURRENCY=32` と書けます。既存の環境変数が `.env` より優先されます。0・負数・整数以外を指定するとエラーになります。

比較には、同じリモートの同じ大容量ファイルを使ってください。`dit pull` は既存ファイルをスキップするため、比較ごとに取得対象のファイルが欠落している必要があります。既存データを残した別の作業ツリーなどで測定してください。

並列数を増やしても速度が変わらない場合は、MinIO などの保存先サーバーと保存先ディスク、接続経路を確認してください。転送中のサーバーの CPU・ディスク使用状況や、リバースプロキシの帯域制限が調査対象です。

## sync の転送が始まるまで時間がかかる

`sync` は、転送前にファイルを列挙し、ローカルのハッシュとリモートでの存在を確認します。ファイル数が多いと、この準備に時間がかかります。`sync plan` に対象一覧の作成中はスピナー、その後は確認済みファイル数を表示します。ファイル本体の転送は、計画の終了後に始まります。

`push` と `sync` の存在確認は、`DIT_TRANSFER_CONCURRENCY` の値を上限に並列で行います。既定値は16です。同じハッシュへの確認は、1回の計画内でまとめます。確認結果は保存せず、次の実行では確認し直します。

## statusの記号

- `?`: scope内に実体があるがポインタがない
- `↓`: scope内で実体が欠落している
- `.`: ポインタはあるがscope外である
- `M`: scope内で実体とポインタのハッシュが異なる
- `S`: 実体はあるがscope外である
- 空白: scope内で実体とポインタが一致している

詳細は[`dit status` Reference](../reference/status.md)を参照してください。

## 同期前に処理を確認したい

```console
$ dit sync --dry-run
```

エラーが出る場合は、`dit status`、scope、認証環境変数、remote設定の順に確認します。`--prune-remote` は孤児remoteを削除する明示的な保守操作なので、問題調査のために安易に使用しないでください。
